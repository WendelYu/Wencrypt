# 同步与冲突协议 v1

> 2026-11-17 更新：首期后端已改为坚果云 WebDAV。此前 OneDrive 首期说明由 [后端变更与构建说明](07-jianguoyun-and-github.md) 覆盖；OneDrive 验证暂停。
## 1. 决策

云端保存不可变加密修订集合，客户端解密后构建每个条目的版本有向无环图。MVP 不采用“修改整个库然后覆盖上传”，不依赖设备时钟、全局锁或一个共享可变 manifest。

这不是全字段 CRDT。对象集合的并集天然可幂等汇集；同条目并发由显式冲突解决版本处理。用较多文件和历史空间换取简单可靠的并发语义；达到测试容量前做性能验证。

## 2. 远端布局和后端接口

AppFolder 下布局：

```text
vaults/<vault_id_hex>/bootstrap.wenc
vaults/<vault_id_hex>/objects/<sha256>.wenc
```

库 UUID 随机且不含用户命名；不上传明文索引/manifest。MVP 不分片目录，避免创建大量目录的请求成本；文件规模以 10,000 修订验证，后续必要时升级布局。

存储抽象：list_objects(cursor)、get_object(hash)、put_object(hash, bytes)、get_bootstrap、create_vault。接口返回分页游标/重试提示/认证失效/配额错误等类型化结果，不暴露业务明文。

- list 必须处理所有页，不能把第一页当完整集合；后端分页不是一致性快照，周期性完整复查保证最终发现。
- put 内容寻址，只有完全相同的字节才能使用相同路径。收到“已存在”、超时或不确定响应时下载校验；相同视为成功，不同隔离并报警，不强行覆盖。
- 不同修改有不同修订与随机加密材料，因此有不同哈希路径；相同重试写相同字节是幂等的。无须把未验证的 If-Match 当核心正确性前提。
- 即使服务允许短暂读取到未完成文件，接收端必须拒绝校验失败对象，延后重试，不能提交半对象。
- bootstrap 只在新随机目录创建；失败重试时核对原字节。禁止自动新建空库覆盖已存在库。
- v1 正常同步不发 DELETE；云端文件删除不是账号条目删除。

WebDAV 后续适配 GET/PUT/PROPFIND/MKCOL；不依赖 LOCK、MOVE 或服务器 ETag 实现合并。具体服务仍需限流、目录列举与上传可见性测试。OneDrive 本地同步目录后置，不能未经适配直接指向 SQLite 文件。

## 3. 本地保存及同步流程

1. 用户编辑时记录基于哪个 revision；保存前核心确认没有未处理冲突或本地版本变化。不能静默覆盖另一个窗口的编辑。
2. 生成新 revision_id，parents 引用用户实际看到的父版本；加密后事务写入对象和 outbox，提交成功才返回“本地已保存”。
3. 同步先拉取新对象，解锁状态下校验并合并；本地已创建版本的父关系不因拉取而修改。
4. 上传 outbox 中原始字节；先上传祖先再上传子版本，但接收端仍需容忍乱序。
5. 上传成功并校验远端内容后才确认对应任务完成；超时重试不重复创建修订。
6. 再做远端发现，计算 pending、conflict 和验证错误状态。远端仍可能出现新修改，UI 仅报告本轮结果。
7. 锁定时只能传输密文，新下载数据进入隔离缓存；解锁验证通过后才影响条目视图。无需 DEK 的传输与“合并成功”分开计数。

Graph 401：刷新 Token 一次，失败后要求重登，不循环重试；429/503：遵守 Retry-After、指数退避和随机抖动；配额不足：保留 outbox 并提示；403：报告权限问题，不自动扩大范围。Token、预授权下载 URL 和 Authorization 头不得进入日志；跨主机下载重定向不转发 Bearer Token。

同步下载并发默认 4；单轮下载预算 64 MiB，未验证缓存上限 128 MiB，达到上限暂停并要求解锁验证，不删除本地已保存对象以腾空间。异常对象重试有退避与次数上限，避免无限循环。首次 10,000 修订发现/下载的耗时和请求数必须实测；不可变小文件协议的网络成本是显式取舍，未通过容量验收前不承诺可扩展到任意规模。

## 4. 版本图和冲突规则

每条目的已知有效修订构成 DAG。revision_id 与 entry_id 必须绑定；父修订应属于相同条目，禁止循环、自引用或同一 revision_id 对应不同明文。

缺少父版本时，修订进入 pending，不能成为有效当前状态；重新列举并获取缺失父对象。持续缺失显示“同步数据不完整”，不把它当作根版本。创建/首次导入的 parents 为空；其他操作不允许空 parents。

head = 当前有效集合内没有后代的版本。正常编辑创建一个指向当前唯一 head 的新修订；并发时保留多个 head。

规则：

- 不同 entry_id 的修改：集合并集，自动呈现双方结果。
- 同条目祖先与后代：呈现后代，祖先保留历史。
- 同条目两个并发修改：多个 head，保留全部，进入冲突视图。即使看起来修改不同字段，MVP 也不自动拼接。
- 同条目并发删除与编辑：冲突视图保留删除意图和编辑内容；默认列表不把它当正常可复制账号，提示解决。
- 同条目多个删除 head：可标为“删除冲突待确认”，不依靠服务器顺序决定；MVP 统一使用冲突界面处理，不创建未经用户确认的自动合并版本。
- 时间戳相同、时钟偏差或 device_id 大小：都不用于选赢家。
- 两个根修订意外使用同一 entry_id：作为冲突处理，不忽略其中一个。

用户解决冲突时选择保留一个版本、手工组合字段或确认删除。创建一个新的 resolve 修订，parents 包含用户检查过的所有 head，结果为完整快照或墓碑。选择旧密码同样保留其他历史，不改写对象。

提交解决前若本地发现新的 head，要求重新确认。远端后来才发现的新并发 head 继续形成冲突。两个设备同时解决同一冲突也可能产生新冲突，仍保留双方；不宣称一次选择就能终止未来并发。

普通编辑在多 head 时暂停，先解决冲突。历史恢复以当前 head 为父，写入旧快照的新版本，不能把旧修订重新设成唯一 head。

## 5. 删除、重装和完整性

is_deleted=true 是不可变删除修订；不能删除远端旧文件来代表删除条目。所有墓碑与历史在 MVP 永久保留，垃圾回收另设跨设备确认/退役协议后才能实现。

旧设备上传已删除条目的祖先时，已有删除后代仍为 head；旧设备在删除前分支上继续编辑时，形成删除/编辑冲突，不静默复活。

远端缺少本地已知对象时提示异常并保留本地副本；修复上传应显式进行，避免误把用户清空网盘当作普通同步。若远端目录消失，暂停同步，不自动建立空库。新设备没有完整性见证，不能检测从未见过的被隐藏对象；不声称防所有服务端回滚。

从备份恢复同一库时，先建立独立恢复视图；用户选择合并后按 revision_id/父图做集合并集。新的安装产生新 device_id；不能靠克隆设备 ID 获得额外权限。

## 6. 验收场景

1. A 离线改密码，B 离线改备注：同步后两版本均在冲突视图，可手工组合，历史完整。
2. A 改条目 X，B 改 Y：自动汇集，无冲突。
3. A 删除 X，B 离线改 X：删除/编辑冲突，无自动覆盖或复活。
4. A 删除 X，旧 B 只上传旧祖先：仍删除。
5. 设备时间相差一年：因果和冲突结果不变。
6. 请求乱序、重复、上传已成功但响应丢失：有效修订无重复，最终 head 集合一致。
7. 子修订先到、父修订延迟：pending 后恢复，不错误展示。
8. 三设备同时编辑、两个设备同时解决冲突：保留所有并发 head，解决后收敛。
9. 云端对象篡改、目录被删、缺页、限流、配额满：本地仍可读写，给出准确状态。
10. 任意顺序应用相同有效对象集合：相同 head 集合与冲突状态；性质测试覆盖交换、结合、幂等及持久重启。

收敛的前提是所有有效对象最终可达、客户端实现一致、用户完成必要冲突选择；不把暂时网络成功当作强一致性保证。
